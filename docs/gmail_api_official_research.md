# Read-only API access to one personal Gmail account

**Research date:** 2026-07-28  
**Source rule:** Official Google documentation only. No Gmail account, credential, or token was accessed.

## Bottom line

For a script or local desktop program used by one person, use a Google Cloud project with the Gmail API enabled, configure the Google Auth Platform for an **External** audience, create an OAuth client of type **Desktop app**, and run Google's installed-application authorization-code flow in the system browser with PKCE. Request only `https://www.googleapis.com/auth/gmail.readonly` if the program must read message bodies or attachments. Google's installed-app code exchange returns a refresh token; store it in the operating system's secure credential store and use it to obtain short-lived access tokens for API calls.

The most consequential choice is publishing status:

- **Testing:** add the Gmail account as a test user. This is fine for development, but the authorization and any refresh token expire seven days after consent because Gmail scopes are outside the identity-only exception. ([Manage App Audience](https://support.google.com/cloud/answer/15549945))
- **In production, still unverified:** this is the practical configuration for durable personal use. Google says verification is not mandatory for a personal-use app with fewer than 100 users; users may proceed through an unverified-app warning. Unverified apps requesting unapproved restricted scopes retain a lifetime cap of 100 new users. This recommendation is an inference from Google's personal-use exemption and production-audience rules, not a separately named Google deployment tier. ([When verification is not needed](https://support.google.com/cloud/answer/13464323), [Manage App Audience](https://support.google.com/cloud/answer/15549945))

## Configuration checklist

1. Create or select a Google Cloud project and **enable the Gmail API** in the API Library. ([Gmail Python quickstart](https://developers.google.com/workspace/gmail/api/quickstart/python), [verification setup guide](https://support.google.com/cloud/answer/13461325))
2. In **Google Auth Platform > Branding**, provide an accurate app name, support email, and developer contact. In **Audience**, choose **External** for a consumer Google account; “Internal” is available only to projects associated with a Google Cloud/Workspace organization and only permits members of that organization. ([Manage App Audience](https://support.google.com/cloud/answer/15549945))
3. During development, leave publishing status at **Testing** and add the Gmail account under test users. Move to **In production** when seven-day reauthorization is unacceptable, understanding the unverified warning and cap described above. ([Manage App Audience](https://support.google.com/cloud/answer/15549945))
4. In **Data Access**, declare only the Gmail scope actually used. In **Clients**, create a **Desktop app** OAuth 2.0 client and download its JSON configuration. Google requires a separate, platform-appropriate client for each platform. ([Gmail Python quickstart](https://developers.google.com/workspace/gmail/api/quickstart/python), [OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies))
5. Keep the client configuration out of public repositories. Installed apps are public clients and are assumed unable to keep a client secret, so a bundled desktop `client_secret` is not a substitute for PKCE or secure token handling. ([OAuth for iOS and desktop apps](https://developers.google.com/identity/protocols/oauth2/native-app), [OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices))

## Least-privilege scopes and restricted-scope consequences

| Need | Narrowest relevant scope | Limitation / consequence |
|---|---|---|
| Read headers/labels but not bodies | `https://www.googleapis.com/auth/gmail.metadata` | Restricted. It cannot retrieve bodies; `messages.list?q=...` is not available with this scope. |
| Search Gmail and read messages or attachments | `https://www.googleapis.com/auth/gmail.readonly` | Restricted. It reads messages **and settings**, despite being read-only. This is the normal choice for message extraction. |
| Read/change mail | `gmail.modify` or broader | Unnecessary for a read-only tool; do not request it. |
| Full mailbox control, including permanent deletion | `https://mail.google.com/` | Much broader than needed; Google says to request it only when immediate permanent deletion is required. |

Google classifies both `gmail.metadata` and `gmail.readonly` as **restricted** scopes. Apps that do not qualify for an exception normally need restricted-scope verification; access to restricted data from or through a third-party server adds an annual independent security assessment. Google lists personal use by one or a few personally known users as a verification exception. Keeping this one-user integration local avoids that third-party-server assessment trigger, but does not change the scope's restricted classification or waive the Google API Services User Data Policy and Gmail developer policy. ([Gmail scope catalog](https://developers.google.com/workspace/gmail/api/auth/scopes), [restricted-scope verification and exceptions](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [Workspace API user-data policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy))

## Installed-app authorization and token lifecycle

- Use the **authorization-code installed-app flow**: generate a fresh PKCE verifier/challenge, open Google's authorization endpoint in the user's system browser, receive the redirect on a loopback/local URI, validate `state`, and exchange the code plus verifier at Google's token endpoint. PKCE with `S256` is recommended. Do not use an embedded webview; the old manual copy/paste (OOB) flow is no longer supported. ([OAuth for iOS and desktop apps](https://developers.google.com/identity/protocols/oauth2/native-app), [OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices))
- Prefer a maintained Google auth/client library. Google's Gmail quickstart demonstrates `InstalledAppFlow` and a local-server redirect, although its plain `token.json` storage is explicitly a testing example rather than a production storage design. ([Gmail Python quickstart](https://developers.google.com/workspace/gmail/api/quickstart/python), [OAuth overview](https://developers.google.com/identity/protocols/oauth2))
- Google's installed-app code exchange returns a refresh token, enabling offline access and new short-lived access tokens without prompting the user. A refresh token is not guaranteed permanent: it can stop working after user revocation, six months of non-use, a Google-account password change when Gmail scopes are present, token-count limits, time-limited consent, or protective/policy action. Code must handle `invalid_grant` by returning to interactive authorization. Google currently limits one Google Account to 100 live refresh tokens per OAuth client ID; issuing another invalidates the oldest without warning. ([OAuth for iOS and desktop apps](https://developers.google.com/identity/protocols/oauth2/native-app), [OAuth token lifecycle](https://developers.google.com/identity/protocols/oauth2#expiration))
- Store access and refresh tokens in platform secure storage—Keychain on macOS/iOS, Keystore on Android, Credential Locker on Windows, or an equivalent encrypted local store. Never log them, send them in plaintext, or commit them. Revoke and delete them when no longer needed. Google now also documents optional DPoP binding for refresh tokens; PKCE remains the core recommendation for desktop authorization-code protection. ([OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices), [OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies))

## Why a service account is not the answer for consumer Gmail

A service account is an identity belonging to an application, not an end user. It normally accesses the application's own data. Access to users' Gmail data through a service account requires a Google Workspace administrator to grant **domain-wide delegation**, after which the service account impersonates a user in that Workspace domain. A personal `@gmail.com` consumer mailbox has no Workspace domain administrator who can grant that delegation, so a service account does not directly unlock it. Use three-legged OAuth with the mailbox owner's consent. ([Google service-account OAuth](https://developers.google.com/identity/protocols/oauth2/service-account))

## Reading mail, searching, and downloading attachments

1. Call `users.messages.list(userId="me")`. It returns message `id` and `threadId`, not full messages. Page through `nextPageToken`; `maxResults` defaults to 100 and is capped at 500. ([messages.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list))
2. Filter with `q` using most Gmail search syntax—for example `from:sender@example.com is:unread`—and/or `labelIds`. Gmail API search differs from the Gmail UI in some respects; notably, dates in queries are interpreted at midnight PST unless expressed as epoch seconds. ([Search and filter messages](https://developers.google.com/workspace/gmail/api/guides/filtering))
3. For every ID needed, call `users.messages.get`. Use `format=FULL` for parsed headers and MIME parts, `format=RAW` for the base64url-encoded RFC 2822 message, or `format=METADATA` when only selected headers are needed. ([messages.get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get), [Message resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages))
4. Walk the recursive MIME `payload.parts`. A part's body is base64url data inline, or its `attachmentId` identifies separately stored content. For the latter call `users.messages.attachments.get(userId="me", messageId=..., id=...)` and base64url-decode the returned `data`. Treat filenames and MIME types as untrusted input; enforce safe output paths, size limits, and file permissions. ([MessagePart / MessagePartBody](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages), [attachments.get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments/get))

## Polling, synchronization, and push

For a local one-user desktop tool, **polling is Google's recommended approach**. Perform an initial/full sync with `messages.list` plus `messages.get`, retain a recent `historyId`, then poll `users.history.list(startHistoryId=...)` for lightweight partial syncs. History is usually available for at least a week but sometimes less; an expired/invalid `startHistoryId` returns HTTP 404 and requires a new full sync. ([Synchronize clients](https://developers.google.com/workspace/gmail/api/guides/sync), [history.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list))

Gmail push notifications are intended for a backend and require Google Cloud Pub/Sub: create a topic/subscription, authorize `gmail-api-push@system.gserviceaccount.com` to publish, call `users.watch`, and use each notification's `historyId` to call `history.list`. A watch must be renewed at least every seven days (Google recommends daily). Notifications can be delayed or dropped, are capped at one event per second per watched user, and therefore still require periodic sync fallback. Google expressly recommends poll-based sync for user-owned devices such as installed apps. ([Gmail push guide](https://developers.google.com/workspace/gmail/api/guides/push))

## Gmail API limits for the bounded reader (as checked 2026-07-28)

### Google-documented facts

**Quota transition and current standard figures.** Google's current Gmail [usage-limits page](https://developers.google.com/workspace/gmail/api/reference/quota) says the limits changed on 2026-05-01. The new standard limits are **1,200,000 quota units per minute per project** and **6,000 quota units per minute per user per project**. A Cloud project created on or after 2026-05-01 is subject to the new quotas. A project that made any Gmail API use from November 2025 through April 2026 continues with its previously set quotas. The current page does not state one numeric legacy quota for those grandfathered projects and also warns that not all projects have the same quotas, so a legacy project's assigned values must be checked in Google Cloud rather than inferred. Google's two transition descriptions do not expressly resolve the narrow case of a project created before 2026-05-01 that had no qualifying November-through-April use; that project's live quota assignment is therefore also a console check, not a safe assumption. ([Google Workspace standardized model](https://developers.google.com/workspace/tools-safety))

Google separately documents an **80,000,000-unit per day per project billing threshold**. As of this check, standard use is available at no additional cost and over-threshold charging is only planned for later in 2026; Google has not published the price or effective date on these pages and promises at least 90 days' notice. Google says that, after that notice, quota-increase requests will require Google Cloud billing, use over the standard daily threshold will generate charges, and the new standard quotas will apply unless a higher quota has already been approved and billing is enabled. The 80,000,000 figure is a billing threshold, not the per-minute request throttle. ([Gmail usage limits](https://developers.google.com/workspace/gmail/api/reference/quota), [Google Workspace standardized model](https://developers.google.com/workspace/tools-safety))

**Relevant per-call costs.** The same [Gmail quota table](https://developers.google.com/workspace/gmail/api/reference/quota) assigns these costs to every request:

| Method | Quota units per call |
|---|---:|
| `users.messages.list` | 5 |
| `users.messages.get` | 20 |
| `users.messages.attachments.get` | 20 |
| `users.history.list` | 2 |

The table gives one cost for `messages.get`; choosing `METADATA`, `FULL`, or `RAW` does not create a cheaper quota class. `messages.get(format=METADATA, metadataHeaders=...)` can restrict the response to named headers, while `FULL` returns parsed body content in `payload`. ([messages.get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get), [message formats](https://developers.google.com/workspace/gmail/api/reference/rest/v1/Format))

**List and attachment behavior.** `users.messages.list` defaults to 100 results and permits at most **500 results per page**. Its `messages[]` entries contain only `id` and `threadId`; the response can also contain a `nextPageToken` and an estimated total result count. It does not return Date, From, To, Subject, snippets, or bodies, so this design needs one `messages.get(format=METADATA)` per displayed candidate to obtain those four headers. The `q` search parameter cannot be used with the narrower `gmail.metadata` OAuth scope; this design's already-required `gmail.readonly` scope supports `q` as well as the selected full reads and attachment retrievals. To preserve the application's 75-candidate Search Bound, request at most 75 and stop after collecting 75 rather than following a page token merely because more matches exist. The API's 500-result ceiling is not the application's privacy limit. ([messages.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list))

For a MIME part whose `MessagePartBody` has an `attachmentId`, downloading that part requires one `users.messages.attachments.get` call and returns base64url-encoded `data`. If the body has no `attachmentId`, its data is already inline in the message response and no attachment-get call is needed. The resource reports the decoded part size in bytes, encoding notwithstanding. ([attachments.get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments/get), [MessagePartBody](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments))

**Accepted application attachment boundary, not a Google requirement:** The ordinary Attachment Download Bound is 25 MiB (26,214,400 decoded bytes) per selected file and 50 MiB (52,428,800 decoded bytes) aggregate per invocation. A larger one-time authorization names the exact attachment, explicit destination, and temporary raised ceiling without changing these defaults. The reader preflights the Gmail-reported decoded size, verifies actual decoded length, installs through a restricted temporary file only after all checks pass, never overwrites, and removes temporary output on failure. Binary MIME data delivered inline with a full-message response remains undisclosed and unsaved under full-message authority; only its descriptor crosses that boundary, and a later selection reacquires the part under attachment-download authority.

`users.history.list` is not needed for a one-shot bounded search. For later incremental polling, it defaults to 100 and permits at most 500 history records per page. Google says a `startHistoryId` is typically valid for at least a week but can rarely be valid for only a few hours; an invalid or stale value typically returns HTTP 404 and calls for a full sync. That recovery condition is not permission for this application to perform an unbounded mailbox read. ([history.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list))

**Batching.** Gmail permits at most **100 inner calls in one HTTP batch** and recommends no more than **50**, because larger batches are likely to trigger rate limiting. A batch containing *n* calls counts as *n* requests for usage accounting, not one; batching reduces HTTP connection overhead but does not reduce quota-unit consumption. Google may execute inner calls in any order. ([Gmail batch requests](https://developers.google.com/workspace/gmail/api/guides/batch))

**Rate, concurrency, bandwidth, and retries.** Quota failures can appear as HTTP 403 with reasons such as `rateLimitExceeded` or `userRateLimitExceeded`. HTTP 429 can indicate a per-user bandwidth limit or the per-user concurrent-request limit; the concurrency form is reported as `Too many concurrent requests for user`. Google says its Gmail API upload/download bandwidth limits are equal to, but independent of, IMAP limits and are shared across all Gmail API clients for the user. The concurrent-request limit is also shared across all Gmail API clients for that user, and many parallel calls or a large batch can trigger it. The Gmail API error page does **not** publish a numeric concurrency ceiling or a numeric consumer-Gmail API bandwidth ceiling. Its linked [numeric bandwidth table](https://knowledge.workspace.google.com/admin/gmail/gmail-bandwidth-limits) expressly applies to Google Workspace editions, so those figures are not asserted for this personal `gmail.com` design; neither missing consumer limit should be invented. Transient server failures can also appear as HTTP 500, 502, 503, or 504. ([Resolve Gmail API errors](https://developers.google.com/workspace/gmail/api/guides/handle-errors))

For time-based quota errors, Google recommends truncated exponential backoff with jitter: waits of approximately 1, 2, 4 seconds and so on, each plus a newly generated random delay of up to 1,000 ms, normally capped at 32 or 64 seconds, with a finite retry limit. The error guide says the first retry period should start at least one second after the error and recommends backoff for rate-limit and backend failures. A 401 should instead cause token refresh and, if that fails, a new OAuth flow. ([Gmail usage limits](https://developers.google.com/workspace/gmail/api/reference/quota), [Resolve Gmail API errors](https://developers.google.com/workspace/gmail/api/guides/handle-errors))

### Calculations for the specified bounded flow

These are arithmetic/design inferences from Google's per-call costs, not separate Google limits:

| Stage | Calculation | Incremental units | Running total |
|---|---:|---:|---:|
| One list call returning up to 75 candidate IDs/thread IDs | `1 × 5` | 5 | 5 |
| Metadata gets for Date/From/To/Subject on all 75 candidates | `75 × 20` | 1,500 | **1,505** |
| Ten additional full-message gets after selection | `10 × 20` | 200 | **1,705** |
| *A* separately stored attachment downloads | `A × 20` | `20A` | **`1,705 + 20A`** |

Thus the candidate list plus headers consumes 1,505 units, or about **25.08%** of the new 6,000-unit per-user-per-project minute quota. Adding ten full reads brings the flow to 1,705 units, or **28.42%**. One separately stored attachment makes the total 1,725; ten make it 1,905. Inline MIME-part data adds no `attachments.get` call. HTTP batching does not change any of this arithmetic. Using `METADATA`, named headers, partial-response `fields`, and gzip can reduce transferred data, parsing, and exposure, but the published method cost remains 20 units per `messages.get`. ([Gmail performance tips](https://developers.google.com/workspace/gmail/api/guides/performance))

For this one-user application under the standard quota, `6,000 units/minute × 1,440 minutes/day = 8,640,000 units/day`, only **10.8%** of the 80,000,000-unit project billing threshold even if the user quota were continuously saturated. This is a mathematical upper-bound inference, not a separately documented Google guarantee; it would need reevaluation if Google changed or approved an increase to the per-user quota.

**Later Transmission Milestone consequence.** The Retrieval and Transmission Desktop clients can remain separate authorization profiles while still sharing the same per-user-per-project and project quota pools because both clients belong to the same Cloud project. A future `users.messages.send` request costs **100 quota units**; Google's quota page also states a maximum of **500 recipients per message**. Separately from API quota units, Google says a personal Gmail account may be temporarily unable to send after more than 500 messages in a day or more than 500 recipients in one message, with sending normally restored within 1–24 hours. Google's API error guide says per-user mail-sending limits are shared across API, built-in/web, and SMTP clients and warns that a successful API response alone does not establish final delivery. These facts do not authorize or alter the separately gated Transmission Milestone. ([Gmail usage limits](https://developers.google.com/workspace/gmail/api/reference/quota), [Gmail personal-account sending limits](https://support.google.com/mail/answer/22839), [Resolve Gmail API errors](https://developers.google.com/workspace/gmail/api/guides/handle-errors))

### Read Bound versus API throttle

**Accepted application decision, not a Google requirement:** Google's limits do **not** determine the privacy/context Read Bound. They are service-capacity and billing controls and permit far more message access than the Operator may have authorized. The Search Bound defaults to 10 and has a hard ceiling of 75. One Operator-authorized read permits at most 10 selected full-message API calls and no more than 1 MiB (1,048,576 bytes) of aggregate canonical decoded body text disclosed to Codex or another consumer. Candidate metadata and attachment binaries are excluded from the body allowance; attachment binaries remain separately selected and subject to the accepted 25 MiB per-file and 50 MiB aggregate Attachment Download Bound. Selected messages are processed in stated order, and the reader emits no partial body or later selected body when the next complete body would cross the allowance. Exact decoded size may become known only after a selected message reaches the local process; a held body is discarded without entering model context, logs, caches, or files. Quota headroom never authorizes another candidate, full message, or attachment.

**Accepted application throttle, not a Google requirement:** Maintain a per-authenticated-user weighted rolling budget of **3,000 quota units per 60 seconds** (50% of the new standard per-user quota), count every call by its documented unit cost, and allow at most **4 ordinary Gmail API requests in flight**. Do not add a fixed requests-per-second delay initially: the 75-candidate application ceiling keeps one search at 1,505 units, while a two-read-per-second cap would force that uncommon maximum search to take at least 37.5 seconds. Do not batch this one-user bounded flow by default. For a retryable rate-limit 403, HTTP 429, HTTP 500/502/503/504, or equivalent replay-safe temporary read failure, pause new dispatch for that user and permit one initial attempt plus at most four retries. Without a usable server delay, wait approximately 1, 2, 4, and 8 seconds plus fresh 0–1-second jitter; stop at five total attempts or a 60-second total retry deadline. Honor a server-supplied delay only when it fits inside the remaining deadline. After exhaustion, return a resumable error instead of retrying indefinitely; repeated concurrency-related 429 responses lower the four-request cap. A 401 follows one normal refresh path and then reauthorization rather than backoff. These read-retry rules never authorize automatic retry of an ambiguous later send. Recheck the live quota page and assigned Cloud Console quotas before implementation or after Google publishes the later-2026 billing transition.

These service controls also do not replace local security controls: keep message caches and downloaded attachments only as long as needed, encrypt sensitive local data where appropriate, prevent path traversal/overwrite when saving attachments, and never expose tokens or mail data through logs, crash reports, backups, or source control. The token-storage requirements are Google's; the attachment hardening steps are ordinary local security controls inferred from handling untrusted email content. ([OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies), [OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices))

## Recommended minimal profile

For one personal mailbox: **External audience; Desktop app client; `gmail.readonly`; installed-app authorization-code flow with system browser, loopback redirect, PKCE S256, and `state`; offline refresh token in OS secure storage; In production if durable access is needed; `messages.list` + `messages.get` + `attachments.get`; periodic `history.list` polling; no service account and no Pub/Sub unless a real backend is justified.**
